### The failing allocation gate, adjudicated

`perfout.txt` (now deleted) recorded `ResultPipeline_DoesNotAllocatePerIteration` failing with 96,168 bytes against a
budget of 8,192 bytes. The gate was **not** too strict and the test was **not** written incorrectly: the run was a
**debug** build, and the allocation had a real cause inside the library.

The chain was: `Result.Ok(int)` -> the `value is null` null guard -> a `box` instruction -> 24 bytes per call for a
value-type payload. Optimized code folds the box away, so the release build passed; unoptimized code does not, so
the debug build failed. The fix is row 2 of the table. The gate now passes in **both** configurations, and
`docs/performance-budgets.md` states that the zero-byte budgets hold in a debug build as well.
